# Taste (Continuously Learned by [CommandCode][cmd])
- Values authenticity — explicitly prohibits fabricated content (fake statistics, testimonials, client logos, company names, or achievements). Confidence: 0.9
- Prefers extremely detailed, numbered, hierarchical specifications covering every section, behavior, and constraint upfront before implementation begins. Confidence: 0.8
- Accessibility-conscious — requires semantic HTML, proper heading hierarchy, keyboard navigation, focus states, and accessible color contrast as a first-class requirement, not an afterthought. Confidence: 0.8
- Performance-conscious — expects optimized images, lazy loading, minimal JavaScript, fast page loads, and never leaving the user with a blank screen. Confidence: 0.8
- Prefers production-quality code conventions: TypeScript strict mode, reusable components, clean folder separation (app/components/data/lib/types), proper error handling, and proper loading states for all async actions. Confidence: 0.7
- Prefers one consistent design system (dark theme, single accent color, subtle gradients, generous spacing) rather than excessive colors or effects. Confidence: 0.7
- Values a consistent global loading system (preloader, button spinners, skeleton states, form submission states) applied uniformly across the entire application, not ad-hoc per component. Explicitly expects the same loader to appear on navigation actions (e.g. navbar button clicks) as everywhere else. Confidence: 0.8
- Prefers a single, identical loader component reused for ALL loading scenarios (initial page load, route transitions, button loading, form submissions) rather than different loader types per context. Confidence: 0.6
- Prefers subtle, professional animations that respect `prefers-reduced-motion` — never excessive, never slowing down the website. Will explicitly revert (ask to undo) if animations feel too elaborate (e.g., gradient orbs, scroll progress bars, stagger reveals, timeline line animations, skill progress bars). Confidence: 0.8
- Prefers CSS-based modern web animations (scroll progress bars, gradient orbs, stagger reveals, scroll-triggered progress bars) over Three.js/WebGL 3D effects. Rejects heavy 3D libraries for visual polish in favor of lightweight, performant CSS animations. Explicitly tells the assistant to remove 3D scenes and animations entirely when they are added without prior approval. However, when the user explicitly requests 3D/Three.js visualizations themselves, expects a sophisticated, interactive implementation with mouse parallax, performance optimization (GPU, prefers-reduced-motion, mobile particle reduction), responsive adaptation across breakpoints, and a configurable, reusable component API. The visual should feel premium, futuristic, and professional — never a basic 2D atom icon or generic spinning globe. Confidence: 0.85
- Expects mobile-first responsive design with responsive typography, spacing, navigation, and touch-friendly targets across desktop, laptop, tablet, and mobile. Confidence: 0.7
- Expects comprehensive SEO metadata (Open Graph, Twitter cards, semantic HTML, proper heading hierarchy) as a built-in requirement, not an optional add-on. Confidence: 0.7
- Prefers pixel-perfect/exact replication of provided visual references (images, design examples) — reproduce them faithfully, not as creative interpretations or approximations. Confidence: 0.6
- Prefers a specific visual aesthetic for loading indicators: glowing tick/line marks radiating outward from center (like a radar or compass), rotating around the text, rather than solid conic-gradient rings or filled spinners. Confidence: 0.7
- Prefers a specific loader animation cycle: lines/build-ticks should appear one by one sequentially around the circle (like building up), complete a full circle, then all vanish at once and restart the cycle — a continuous "build → hold → clear → repeat" pattern. Not a one-shot deceleration or simultaneous appearance. Confidence: 0.7
- Prefers navigation loaders to be transparent/non-blocking overlays: the loader should appear centered on screen without a solid background overlay, so the page content remains visible behind it during navigation. Do not use a black or opaque background that obscures the page. Confidence: 0.6
- Prefers a "pending changes" workflow — wants to be able to revert/undo changes after seeing the result, and will explicitly signal approval (e.g. "yes") before changes are considered final. Do not treat changes as committed until user confirms. Confidence: 0.6
- Prefers to handle destructive/npm/package-management shell commands themselves — will explicitly stop the assistant from running commands and take over in their own terminal (e.g. PowerShell). Do not run commands that delete node_modules, package-lock, or perform clean installs without asking first. Confidence: 0.5
- Prefers a zero-friction local dev setup where `npm run dev` is the sole command needed to start working — no separate build steps, no configuration commands, no multiple terminals required. The dev server must NOT trigger any implicit dependency downloading or installation during `npm run dev`; all dependencies must be fully pre-installed so that the command purely starts the dev server with no side effects. Expects the project to "just work" with that single command. Confidence: 0.7
- Expects defensive/resilient data handling — if a data field is removed from a data file (e.g. `period` on an experience entry), the code should gracefully handle it without TypeScript errors and without rendering empty UI elements (e.g., empty badge spans). Prefers optional types and conditional rendering over required fields that would break when data is simplified. Confidence: 0.5
- Prefers preserving static/SSG rendering over opting pages into dynamic rendering — when a component uses browser-only libraries (e.g. Three.js), prefers component-level SSR guards (useEffect mount check with placeholder) rather than exporting `force-dynamic` on the page. Explicitly rejects `force-dynamic` as a solution. Confidence: 0.9
